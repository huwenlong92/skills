# Webhook 子任务

适用范围：检查、配置、生成或发送 Docker 项目的发布通知，以及通知失败后的独立补发。必须读取本文件；项目文件位置以[固定布局](project-layout.md)为准，涉及镜像发布时追加[业务构建发布](project-release.md)。路径均相对目标项目根目录。

## 调用与职责

下列是 Skill 自然语言子任务约定，不是已注册的系统 dockerops CLI。Agent 必须解析用户意图，再检查实际项目脚本和根 Makefile；禁止把示例文本直接作为不存在的系统命令执行。

| Skill 子任务 | 必须完成 | 禁止执行 |
| --- | --- | --- |
| dockerops webhook check | 定位环境和脚本，静态检查配置来源、服务映射、通知目标数量、缺失项与实际副作用，输出脱敏结果 | POST、GET、HEAD、探测通知 URL、执行 webhook.sh、构建、推送、部署 |
| dockerops webhook setup | 核对需求后生成/调整项目 webhook.sh、公开路由声明及根 Makefile 入口，再离线验证 | 自动发送、覆盖既有凭据、迁移无关环境或修改服务器 |
| dockerops webhook send | 核对已发布版本、目标环境、服务和授权后，调用本项目已有通知入口并分别报告结果 | 构建/重发镜像、切环境、通知全部服务、盲目重试或将响应成功视为已上线 |

只有用户明确要求发送，或当前项目规则/会话已有对应授权时才允许 send；“看看配置”“检查 webhook”“补齐脚本”只允许 check/setup。已确认的授权必须沿用，禁止重复要求相同确认。

## 项目入口与路由

- 单环境必须使用 `.sdkit/docker/webhook.sh`，多环境必须使用 `.sdkit/docker/<环境>/webhook.sh`。根 Makefile 提供 webhook 或 webhook-<环境>，禁止创建独立子目录 Makefile。已有旧布局必须先审计，未授权迁移时只能复用旧路径并报告差异。
- 必须按“当前项目 → 明确环境 → 明确服务 → 目标列表”匹配。一个服务允许对应多个目标；通知不得隐式扩展到其他环境或服务。当前用户或已有任务不能唯一确定环境/服务时必须询问，禁止默认 release、all 或第一个目标。
- 每个目标必须有稳定、不含秘密的标识，供结果和定向补发使用；必须核对重复标识/重复目标，禁止静默覆盖或重复通知。单前端项目可以使用其已声明服务名；旧脚本以 `-` 表示本组件时必须保留其真实含义，禁止将 `-` 解释为所有服务。
- 发布脚本已通知过的目标，Agent 禁止在外层再调用一次。setup 修改聚合发布行为时必须说明调用关系，防止根 Makefile、publish.sh 与外层 Agent 三处重复通知。

公开的 config.json 只允许保存路由和秘密引用，例如：

```json
{
  "webhooks": [
    {"id": "worker-a", "service": "worker", "url_env": "WORKER_A_WEBHOOK_URL"},
    {"id": "worker-b", "service": "worker", "url_env": "WORKER_B_WEBHOOK_URL"}
  ]
}
```

URL 值由运行环境或已确认的私有配置注入。实际项目脚本必须实现该声明的读取与校验，禁止仅写 JSON 就宣称通知可用。已有 service/url 格式可以经审计后保持兼容，不得在未授权迁移时强制改格式；真实 URL/Token 禁止进入脚本、项目 config.json、README、镜像、日志或共享 Skill。

## check：离线与脱敏

- 必须只读检查脚本、根 Makefile、环境配置及已存在的私有引用；Shell 语法允许使用 bash -n/sh -n，禁止运行通知脚本、source 配置或假定 make -n 没有副作用。
- 必须分别报告 configured、unconfigured、invalid，及每个选定服务的匹配目标数量；没有目标必须报告“未配置/未匹配”，禁止因旧脚本 exit 0 就声称通知成功。
- 必须识别有限超时、请求方法、成功状态、失败退出、是否自动重试，以及 endpoint 是否触发运行更新。check 不验证 URL 的网络可达性，禁止以 GET/HEAD/POST 探测通知地址。
- 必须只输出目标 ID、环境、服务、配置来源是否存在及参数完整性，禁止输出秘密值、含 Token 的 URL、请求体或响应正文。检查旧硬编码脚本时必须先脱敏再展示，禁止 cat、完整 diff 或打印原始 JSON。

## setup：生成与兼容

- 必须先检查项目是否已有 webhook，核对当前环境/服务以及一服务多目标关系。无通知需求时禁止生成空脚本或猜造地址；已有环境暂时无目标时必须保留并记录其可选/必需策略。
- 生成脚本必须设定有限超时，只执行已核实的通知协议；已有 HTTP POST 入口不得擅自添加 payload、签名、请求头或改用其他方法。目标不明确时必须先确认协议，禁止用占位 URL 试发。
- 默认禁止自动重试或跟随重定向；只有项目明确要求、目标幂等性与认证边界已核实时才允许相应行为。超时可能已触发远端动作，禁止将网络错误直接视为未执行。
- 必须在项目文档说明每个目标的用途和是否引起自动更新，配置注入方式、调用时机、超时、失败行为和脱敏结果；禁止在 Skill 私有配置新增另一份项目目标清单。用户显式指定私人配置文件时必须遵守其位置并保护已有内容；若确需新增 Skill 级私人配置，必须使用 `~/.config/sdkit/skills/dockerops/config.json` 并保留既有镜像库绑定，禁止复制现存目标制造第二事实源。

根 Makefile 的通知入口典型形态（已确认 test 环境、脚本支持服务参数）：

```make
.PHONY: webhook-test
export SERVICE
webhook-test:
	@case "$$SERVICE" in api|worker) ;; *) echo '请指定项目已声明的 SERVICE' >&2; exit 2 ;; esac
	bash .sdkit/docker/test/webhook.sh "$$SERVICE"
```

示例中的 api/worker 允许列表必须替换为本项目实际服务。实际执行是本项目存在的 `make webhook-test SERVICE=worker`。Makefile 和脚本必须校验服务为已声明标识；禁止把未经校验的任意字符串拼进 shell。单环境使用无 test 后缀入口。

## send：范围、结果与补发

- 聚合发布已获通知授权时，必须按构建 → 推送 → 远端验证 → webhook 顺序执行；前置阶段失败禁止继续通知。单独 send 必须核对本次发布版本和选定目标，不能因已发过镜像就猜测应更新哪个环境。
- 显式 send 没有匹配目标或秘密引用缺失时必须停止发送并报告未通知；发布链中明确允许无通知目标时，必须报告 skipped，不能记为 notified。禁止把未配置当成发送成功。
- 对多目标必须逐个记录成功、失败和未知结果，并汇总目标 ID；项目策略允许继续其他目标时可以完成本次名单，其余目标禁止因一个失败被偷偷标成功。存在失败时入口必须返回非零；部分成功必须明确报告 partial，不能只返回整体“成功”。
- webhook 失败必须分别报告“镜像已发布”和“通知失败/结果未知”；补发只能覆盖用户要求或已授权重试且未成功的目标。已成功目标禁止默认重发，超时等未知结果必须先确认远端实际状态，禁止盲目重试、重新构建或重新发布镜像。
- HTTP 2xx 只代表通知入口接受请求；运行更新与业务健康必须按项目发布流程另行验收。输出禁止泄露请求 URL、认证、请求/响应正文。

正向形态：check 得到 worker 的两个目标 → 按授权 send → a 成功、b 失败 → 报告 partial 并只评估 b 的补发。反例：check 发一次“测试 POST”，或一个目标超时后重跑整批发布并再次通知所有目标。

## 验证与完成标准

setup 必须先做 Shell 语法检查，再在隔离 fixture 用替身 curl/HTTP 客户端验证：环境/服务过滤、一对多、零目标、缺失秘密、2xx/非 2xx/超时、失败退出、不自动重试、不输出凭据、成功目标不重复通知；禁止用真实 endpoint 做回归。人工核对上游协议、更新副作用、幂等性及未知结果处理。交付必须区分配置检查、脚本生成、通知发送、部分失败和真实运行状态，禁止将规范或 fixture 通过说成生产已通知。
