# 业务 Docker 构建发布

适用范围：用户要求 Docker 构建、推送、镜像发布、运行环境更新或回滚。修改/生成文件还必须读取[固定布局](project-layout.md)与[项目生成](project-generation.md)；基础镜像库同步和共享 builder 发布仍以[同步与发布](publication.md)为准。所有路径以目标项目根目录为基准。

## 范围与执行前检查

- 必须先确定当前用户要求的是生成文件、仅构建、构建并推送、镜像验证，还是更新运行环境；现有会话已明确的授权必须沿用，禁止逐步重复索取确认。未明确的环境按布局 reference 询问，不能默认正式环境。
- 用户说“Docker 构建发布”时，必须在已确认目标内完成必需文件生成、检查、构建、推送与镜像验证；缺少环境、镜像或架构等必要信息时只停止对应步骤。禁止把它自动扩大为服务器重启、webhook、镜像删除或 Git 提交。
- 必须静态读取 Makefile 与实际调用脚本，检查 SSH、curl、webhook、image rm、prune、配置覆盖和隐式部署。旧目标存在未授权副作用时，必须选择已确认无这些副作用的现有入口或先按范围调整；无法安全拆分时必须报告阻塞，禁止仅凭目标名执行。
- 必须核对 Docker 引擎/context、registry 身份和目标权限、Git 分支/dirty/远端、已确认版本、服务、平台、构建参数与数据挂载边界。认证、平台、目标或配置无法核实时必须停止，禁止切换其他 registry/主机试发。

## 构建、推送与版本

1. 必须按[镜像选择](selection.md)核对真实基础镜像与 runtime 依赖，再使用项目真实 build 入口。基础镜像双架构不要求业务双架构，禁止顺带重建全部服务或共享 builder。
2. 必须记录本次明确版本、源码 revision、环境、平台和服务范围。项目无版本规则时必须在 README 定义本次唯一版本及别名策略后执行；使用唯一版本加 latest 时，必须保证整个发布范围沿用同一个明确版本。
3. 推送前必须核对本地制品的版本标签/label 和平台。需要不可变版本时必须核验远端是否已存在；网络/权限错误不能当作版本不存在。已存在或发布结果不确定时必须先核对 digest，禁止盲目覆盖、重发或用新版本掩盖失败。
4. 必须先推送并验证明确版本，再更新所选环境的可移动别名；只有项目明确授权时才允许维护 latest。更新后必须核对明确版本和别名 digest 一致，平台与目标相符。
5. 构建失败停止推送；推送或远端校验失败保留制品和现场，禁止继续更新别名或宣称全部完成。多服务必须报告已成功与未成功服务，不能将部分成功说成整批发布成功。

正向形态：确认 test 和单服务 → 构建明确版本 → 核对本地版本/平台 → 推送版本 → 验证后更新该环境别名。反例：自动使用所有服务、覆盖 release latest，再根据 webhook 200 宣称已上线。

## Webhook 通知

检查、配置、发送、空目标处理、一服务多目标、补发与脱敏必须统一执行 [Webhook 子任务](webhook.md)，本文件不维护第二套通知协议。镜像发布与通知必须分别报告结果，通知失败不能触发重建或重发镜像。

## 运行更新、静态制品与恢复

- 只有当前用户或目标项目已有对应授权时才允许运行部署/恢复入口；部署前必须核对主机、Compose 文件/项目名、服务范围、版本、端口、网络、配置和持久化数据，保护现有运行配置与回退依据。
- Compose 相对路径必须按实际 Compose 解析基准核对，禁止把文件移动到 `.sdkit/docker/<环境>/` 后仍假定挂载相对源码根目录；必须记录服务器实际放置位置和使用方式。
- 更新必须按选定范围验证 Compose，再拉取所需镜像并更新所需服务；禁止自动启动不相关基础设施、全局清理、down -v 或删除未知 orphan。检查容器 image ID/digest、健康状态和真实业务入口，禁止只看容器进程。
- 静态制品必须按已确认方式提取、备份和发布到目标入口；禁止启动 scratch 制品容器。必须验证首页、资源路径、缓存与旧资源兼容，发布失败保留恢复材料。
- 新 publish.sh 默认不触发 webhook 或服务器操作；需要自动更新时必须独立提供已授权入口并在 README 记录。已有项目迁移不得静默改变原有自动更新机制。
- 回滚必须确认已验证旧版本、运行配置和数据兼容性；涉及 schema/数据变更时镜像回退不能代替数据恢复计划。缺少回滚条件时必须标为未实现，禁止生成虚假可用 rollback.sh。
- 本地镜像/缓存清理必须另有当前用户或项目明确授权，只能处理本次已确认制品；禁止全局 prune、删除历史回滚标签或把清理混入新 publish 默认流程。

## 完成标准

必须分别报告生成与验证、构建、推送/远端 digest、别名、webhook、运行更新及业务健康的实际状态；未要求或未运行的阶段明确标为未执行。README 的命令与副作用必须准确，失败阶段及保留制品必须可追踪。人工检查授权与服务范围、发布失败恢复、持久化数据/凭据保护和实际入口验收，禁止把 push 成功等同于已上线。
