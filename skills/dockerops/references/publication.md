# 同步与发布

适用范围：镜像库没有所需镜像/版本线、锁文件缺失或不一致、需要同步升级或新增共享 builder。执行这些修改前必须读取本文件及[镜像选择与接入](selection.md)。

涉及镜像源码库或消费项目的定位、Git 同步与跨会话检查，必须执行[配置与仓库协作](repository.md)；镜像发布授权仍以本文件为准。

本文件仅定义基础镜像库和共享 builder 的发布流程；业务项目镜像必须读取[业务构建发布](project-release.md)，禁止将本文件的镜像库授权扩展到业务运行环境。

## 发布前提与停止条件

- 必须读取镜像库 `AGENTS.md`（存在时）、README、Makefile、对应目录及发布脚本，检查 `git status --short`，保留已有改动。本文件定义基础流程，明确声明这些仓库文件是具体目标地址、维护入口和授权范围的来源；没有这些文件时必须停止并说明仓库布局不匹配。
- 仅当用户已要求缺失时自动补同步，或镜像库显式规则已有对应持续授权时，允许新增并发布所需镜像。Git 提交与推送必须另有当前用户或该镜像库的明确授权；不能从“生成 Dockerfile”推导任意仓库的 Git 发布授权。
- 官方来源必须通过上游官方文档/registry 在线核验实际标签和 amd64、arm64 两个平台；Docker Hub 官方镜像使用 `docker.io/library/<name>:<tag>`，Docker 官方 frontend 使用经核验的官方维护来源。禁止把第三方或私有镜像未经明确许可纳入原样同步清单。
- 上游缺任一平台、身份无法确认、目标标签碰撞、凭据不可用、平台/config 或 digest 验证失败时必须停止本次发布，不降级为单架构，不替换其他版本，不覆盖历史回滚标签。
- 网络超时或服务端暂时错误允许在已授权执行入口再试一次；仍失败必须停止并报告阶段。401/403、无效配置、digest 冲突或缺少平台禁止原样重试。禁止请求用户把凭据贴进会话或写入代码。

## 新增或补同步官方镜像

1. **核对是否已存在。** 同版本线已有配置但发布异常时必须修复该条目，禁止新建重复目录掩盖失败。没有匹配版本线时按 `<镜像名>/<版本线>/` 新建目录；仅允许在镜像库配置目录存放 `image.conf` 和同步产生的 `digest.lock`，禁止放进消费项目或技能源码。
2. **建立配置。** `image.conf` 只允许定义以下三项，目标组织从镜像库声明解析。以下为脱敏示例，不证明该版本已发布：

   ```bash
   SOURCE_IMAGE=docker.io/library/node:22-bookworm-slim
   TARGET_IMAGE=registry.example.invalid/mirror/node:22-bookworm-slim
   PLATFORM=linux/amd64,linux/arm64
   ```

   新建条目必须同时更新 `images.txt`、根 `README.md` 的目录树和镜像表，完整列出目录、上游与目标地址。禁止复制其他版本的 `digest.lock`；原有锁文件只能由成功同步更新。
3. **执行单项同步。** 在镜像库根目录执行 `make sync IMAGE=<目录>`。必须在线解析上游并按 digest 复制两个平台的 manifest、config 和 layers，再发布双平台索引；禁止用单平台 `docker pull/tag/push` 或 `USE_LOCAL_CACHE=1` 冒充多架构同步。仅当当前任务覆盖全库时允许 `sync-all`。
4. **验证发布。** 执行 `make verify IMAGE=<目录>`，核对配置与真实锁文件、普通/回滚标签的目标索引 digest、两平台子 manifest 与 config。目标过滤了其他架构/attestations，源/目标索引 digest 可以不同，但对应两个平台的子 manifest digest 必须相同。
5. **回拉最小验收。** 读取 `scripts/smoke-image.sh` 是否支持当前镜像和版本断言。支持时执行 `make smoke IMAGE=<目录>`；不支持新镜像或断言仍写死旧版本时，必须补充匹配的两平台检查，或执行等价的两平台回拉与最小版本/功能检查。工具链检查版本；frontend 执行两个目标平台的最小构建；服务镜像禁止带业务配置、数据卷或网络启动常驻服务。禁止将“脚本退出成功”替代实际预期版本检查。

修改 Shell 脚本后必须执行相应 `bash -n`/`sh -n`；修改发布/验证逻辑时必须运行镜像库已有离线保护测试。日常镜像同步不得重建官方镜像。

官方同步使用执行主机既有 Docker 认证和 registry 工具，不依赖 Docker daemon/context；仅当用户明确指定时允许通过 `SYNC_HOST` 转至对应 SSH 主机。回拉验收使用当前 Docker context 或明确授权的本机 context，禁止擅自切换远端主机。

## 派生 builder

- builder 必须独立保存配方、README、发布脚本与真实发布锁文件，禁止加入供原样同步使用的 `images.txt`。新增目录必须更新根 README 的目录树和 builder 说明。
- 必须使用已同步、按双架构目标索引 digest 锁定的基础镜像；工具链版本、Dockerfile、断言、文档和发布脚本必须一致。业务依赖与凭据的放置规则以[选择 reference](selection.md)为准。
- 必须先读取匹配 builder 的 README，再使用其声明的 build/verify/publish 入口；禁止硬编码某个历史 Go 版本的目录或把官方同步入口用于 builder。
- 两个平台必须分别构建、禁网依赖检查与最小编译运行，发布唯一双架构版本，并完成远端回拉验收后才能更新版本线别名。平台制品标签只允许用于组装/检查索引，禁止作为双架构日常消费引用。
- 发布锁文件必须由成功发布流程产生。禁止手写 digest、复用旧发布时间或把本地构建成功表述为 SWR 已发布。

## Git 与消费项目交付

发布成功且已有 Git 提交/推送授权时，必须再次检查状态与差异，只暂存本次配置、配方、文档、脚本和锁文件；禁止 `git add .`、`git add -A`、`git commit .`、强制推送及修改 remote。必须使用已有远端并核对推送结果；权限仅适用于有该授权的镜像库，不扩展到消费项目或技能库。

发布或验收失败必须保留现场并报告错误，禁止提交为“发布完成”或生成伪造锁文件；成功的远端发布不会因为 Git 推送失败而自动回滚。仅 Git 推送失败时必须明确区分“镜像已可用”与“源码记录尚未推送”，禁止重新发布以掩盖 Git 错误。

补齐后返回选择流程，使用锁文件中的实际目标引用更新消费项目。禁止触发业务 Webhook、部署、数据库操作、删除标签或清理镜像。

## 完成标准

- 官方镜像：配置与清单/README 一致，真实锁文件来自本次成功同步，普通与回滚标签均通过远端双平台检查，两平台最小验收通过。
- builder：配方、工具链断言与文档一致，唯一版本和别名均为已验证双架构发布，真实发布锁文件完整；未混入官方同步清单。
- Git：仅在已有授权时提交/推送本次相关文件，并记录结果；无授权时保留本地改动并明确未提交，禁止谎称已同步源码远端。
- 消费：使用已验证真实地址，保持项目版本/系统/业务架构；交付中分别报告镜像发布、Git 同步和业务构建状态。人工核对发布范围和未完成事项。
