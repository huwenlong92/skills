# 配置与仓库协作

适用范围：镜像库绑定、私有配置迁移、本地目录定位，以及镜像源码库或消费项目的 Git 写入。修改配置读取脚本、镜像发布入口或 Git 协作规则前必须读取本文件。项目文件路径以对应仓库根目录为基准；`~` 仅表示执行用户的主目录。

## 私有绑定与迁移

- 默认私有配置必须位于 `~/.config/sdkit/skills/dockerops/config.json`。`catalog.py` 与 `binding.py` 的 `--config <path>` 必须覆盖 `DOCKEROPS_CONFIG`，两者均未指定时才允许使用默认路径；禁止自动回退旧路径。目录覆盖的完整顺序以[镜像选择与接入](selection.md)为准。
- 配置必须以 `repository.local_path` 保存镜像库本地目录、以 `repository.url` 声明预期 SSH/HTTPS Git 远端。相对目录必须以配置文件所在目录解析；URL 禁止携带密码、Token、查询参数或片段。禁止用本机当前 Remote 自动覆盖已经声明的 URL。
- 配置只允许保存在用户配置目录或用户显式指定的私有位置；禁止放进 Skill 安装目录、源仓库、业务项目或要求在项目 AGENTS.md 写死个人目录/仓库地址。只有存在用户确认的目标时才允许创建配置，禁止初始化空绑定、记录镜像清单或存放 registry 凭据。
- 旧版 `dockerops/config.json` 不自动读取。旧 `mirror_repo` 字段仅用于显式配置的迁移兼容，不能证明远端身份。迁移前必须校验 JSON、解析旧目录，确认预期远端 URL 来源；只有本地 Remote 而无用户确认时，必须先核对目标，禁止将未知 Remote 自动当作授权声明。
- 迁移必须确认目标不存在；目标存在时必须停止覆盖。相对旧路径必须转换为与旧解析结果相同的目录，禁止原样复制到更深目录导致漂移。必须使用排他创建、`0600` 权限，核对内容、路径和全部 Fetch/Push URL，并用新脚本实际查询；原文件必须保留，只有用户要求清理时才允许删除。禁止顺带迁移其他工具的认证配置。

正向配置形态（目标必须替换为用户确认的绑定）：

```json
{
  "repository": {
    "local_path": "../../repos/image-mirror",
    "url": "https://code.example.invalid/team/image-mirror.git"
  }
}
```

反例：把上述占位地址当作真实远端，或复制旧相对路径后未验证其含义。

## 当前仓库与身份

- 必须检查明确绑定的镜像目录，读取当前 `AGENTS.md`、README 和清单。消费项目与镜像库必须分别识别，禁止因为同名目录或历史会话就视为同一仓库；绑定路径不可访问时必须停止，禁止扫描主目录猜造替代位置。
- 不建立 Workspace、Primary/Active 或 Provider 切换机制。`catalog.py` 只负责本地文件的离线查询，禁止让配置迁移顺带执行 Clone、Fetch、Commit 或镜像发布；已有合法本地目录不要求先成为 Git 仓库才能查询。
- 仅在 Git 写入任务中，必须从当前用户指令或用户配置取得预期 URL；未配置时允许使用目标仓库的明确声明。必须核对 `origin` 的全部 Fetch/Push URL 与目标一致。比较必须保留主机、非默认端口和路径身份，只允许已核实的 SSH/HTTPS 等价形式；冲突 URL 或缺少 origin 时必须停止，禁止自动修改 Remote。
- 匹配仓库有脏工作树、分叉或身份冲突时，必须停止受影响自动同步并保护现有内容。用户明确要求修改已有未提交内容时，必须先核对归属和文件范围，禁止清理其他任务内容。

## 只读绑定检查

[绑定检查脚本](../scripts/binding.py)只读取当前 Skill 的私有绑定。

在实际 Skill 目录运行以下脚本；只有用户已配置绑定时才允许省略 `--config`：

```bash
python3 <skill-dir>/scripts/binding.py
python3 <skill-dir>/scripts/binding.py --config <private-config.json>
```

脚本必须核对本地目录的 Git 根目录与 origin 的全部 Fetch/Push URL，输出分支、dirty、上游和缓存 ahead/behind；禁止修改配置、Remote、分支或文件，禁止联网或自动 Fetch。`identity_verified` 只表示配置与本地 Remote 匹配，`fresh_remote_check: false` 不能作为远端实时状态或发布许可。

## 双阶段同步与跨会话

1. 修改前必须检查当前分支、工作区、上游与目标文件归属，再按需 Fetch；仅工作区干净且能快进时允许 `git pull --ff-only`。无上游、Detached HEAD 或分叉时必须停止自动同步，禁止自动 Checkout、Stash、Reset、Rebase、Clean 或强推。
2. 写入镜像库或消费项目之前，必须读取目标仓库最新协作规范，检查远端默认分支和开放 PR 摘要。默认分支必须从远端发现，禁止固定为 main。只对同文件、同镜像/版本线、同 builder 或显式依赖 PR 深入读取 diff；只读目录查询不要求全量 PR 扫描。
3. 并行修改必须比较配置、配方、锁文件与发布目标，保留双方意图。未解决冲突或无法取得必要实时证据时，必须停止受影响写入，保留草稿与未合并工作；感知检查禁止触发 CI、镜像发布或部署。
4. 推送前必须再次 Fetch，核对远端 HEAD、全部 Fetch/Push URL、上游、权限和授权，再重新验证。远端前进时必须先比较并安全整合，禁止直接覆盖或强推；远端要求 PR/MR 时必须遵守，不得自动推送默认分支。
5. 只允许暂存本次镜像或 Dockerfile 接入相关文件；Git、镜像发布与业务部署授权必须分别判断。基础镜像库与 builder 发布以[同步与发布](publication.md)为准，业务项目构建发布以[业务构建发布](project-release.md)为准。

正向形态：明确绑定 → 本地身份和状态检查 → 检查关联 PR → 授权范围内修改并验证 → 再核验远端后推送。反例：只改第一个同名目录、忽略第二个 Push URL，或用远端 API 覆盖本地尚未提交的配方。

## 完成标准

必须报告配置来源、镜像库与消费项目身份、分支/dirty/上游状态、PR 关联与未验证能力。配置迁移必须证明解析目标相同、权限为 `0600`、原文件保留且新脚本查询成功；Git 写入必须有验证和授权证据。人工检查 URL 等价性、冲突取舍及发布范围；禁止把目录查询成功称为远端镜像可用或已发布。
