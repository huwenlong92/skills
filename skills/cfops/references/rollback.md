# 失败与回滚

适用范围：部署失败、响应丢失、回退版本、恢复中断会话时必须读取。

## 停止与恢复

- 必须保留源码 SHA、目标、构建摘要、已知部署标识和失败阶段；禁止因失败删除未知工作区、重写历史或重新发布覆盖证据。
- 网络中断、超时和 CLI 非零不证明云端未部署；必须查询 Provider 实际状态，确认是否已完成、是否存在并行新部署，再决定重试。
- 回滚必须有明确的目标环境、指定可用版本与当前授权；禁止把普通部署授权推导成自动回滚授权，禁止简单取“列表上一条”而不核实可用性。
- 必须比较当前与目标版本的 Binding、Secrets、DO migrations、外部资源和静态产物；资源被删除、Schema 不兼容、平台限制或并行发布未核实时停止。禁止以应用回滚宣称 R2、KV、D1 或其他外部数据已恢复。
- 正式数据库禁止 AI 查询、备份或恢复；需要数据库兼容证据时仅使用已授权离线资料，缺证据时报告阻塞。

## 平台差异

- Worker 必须按锁定 CLI 和 [Worker 回滚文档](https://developers.cloudflare.com/workers/versions-and-deployments/rollbacks/)选择明确版本，核对平台当前限制后执行。
- Pages 必须按 [Pages 回滚文档](https://developers.cloudflare.com/pages/configuration/rollbacks/)核实可回滚的生产部署；禁止对 Pages 使用 Worker rollback 命令，禁止把 Preview 一律视为可直接回滚到生产。
- 回滚后必须从 Provider 读回实际部署，再执行 [上线验收](verification.md)。恢复到旧应用版本不意味着恢复了域名、访问策略、定时任务或外部资源。

正向：指定一个已验收且资源仍兼容的生产版本，经当前授权回退后核对 Provider 与正式域名。

反例：新版本返回 500，脚本自动回退并宣称数据库和内容版本一起恢复。

## 完成标准

回滚前后部署标识及兼容证据可核验；未获授权的资源和数据未操作；实际访问单独验收。缺少授权或兼容证据时交付精确候选和阻塞条件，不执行写入。
