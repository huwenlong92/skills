# 软件安装文档规范

本规范适用于 Linux 服务器软件、数据库、中间件、运行时、CLI、守护进程等安装与升级文档。目标是让文档可执行、可验证、可升级、可回滚，而不只是给出一组“当前机器上碰巧能运行”的命令。

## 适用场景

创建或更新以下内容前读取本规范：

- Linux 软件安装、部署和初始化文档。
- “安装最新版”“安装 stable/LTS”“指定版本安装”等版本型文档。
- 官方仓库、发行版仓库、便捷脚本、源码编译、容器镜像等安装方式对比。
- 软件升级、降级、卸载、迁移和安装故障排查文档。

## 基本原则

- 默认优先官方文档、官方软件仓库、官方源码和官方签名，不把第三方博客作为命令的唯一依据。
- 涉及版本、支持系统、仓库地址、签名密钥、依赖和安全公告时，写入前必须联网核验，并记录核验日期。
- “最新版本”必须说明具体含义，例如 `mainline`、`stable`、`LTS`、`latest GA` 或预发布版，不能只写模糊的“最新”。
- 默认推荐最易维护、升级和回滚的官方软件包方案；源码编译是有明确需求时的补充方案，不应伪装成无成本的通用首选。
- 命令需要可复制执行，但不能为了“一键安装”隐藏关键判断、权限边界或破坏性操作。
- 文档中的当前版本号是带核验日期的快照；执行时仍应以官方源的实际候选版本为准。

## 写入前检查

写入新文档前必须：

1. 搜索已有同主题文档，优先更新或建立关联，避免重复。
2. 确认目标软件的官方安装页、下载页、版本页和安全公告入口。
3. 确认受支持的发行版、版本代号、CPU 架构和 init 系统。
4. 区分新装、覆盖安装、迁移和升级；已有安装不能直接套用新主机命令。
5. 检查可能冲突的软件包、服务、端口、数据目录、系统用户和动态模块。

## 文档必须包含的内容

### 1. 结论与适用范围

- 开头说明推荐安装方式、选择理由和不适用场景。
- 写清软件名称、开源版或商业版、版本分支、核验日期。
- 列出支持的 Linux 发行版、版本和架构；范围太大时至少链接官方支持矩阵。
- 说明命令以 `root` 还是具备 `sudo` 权限的普通用户执行。

### 2. 安装方式选择

至少评估以下方式，并说明为什么包含或排除：

- 发行版自带仓库。
- 软件官方仓库。
- 源码编译安装。
- 官方便捷脚本。
- 容器镜像或静态二进制。

如果软件官方提供源码且用户要求“最新版”、自定义模块、编译参数或底层依赖，安装文档必须包含源码编译章节，或链接到同专题下独立的源码编译文档。

安装方式对比至少说明：

- 版本新旧。
- 安全更新来源。
- 配置和数据目录。
- 服务管理方式。
- 动态模块或插件兼容性。
- 升级、回滚和卸载成本。

### 3. 安装前检查与备份

- 系统版本、版本代号、架构和内核信息。
- 端口、进程、服务和软件包冲突。
- 已有配置、编译参数、模块、数据和证书备份。
- CPU、内存、磁盘等必要资源条件。
- 覆盖安装、移除冲突包、替换二进制等操作的影响范围。

不得把删除数据目录、清空配置、递归删除或强制覆盖混进普通安装步骤。确实需要时，必须单独标注破坏性影响、精确目标和恢复条件。

### 4. 软件包安装

- 使用官方推荐的仓库格式和包管理器命令。
- 导入签名密钥后核对完整指纹；记录密钥有效期或轮换提醒。
- 检查候选包来自预期仓库，再执行安装。
- 说明 stable、mainline、LTS 等仓库切换方式。
- 安装后配置开机启动，并说明 systemd、OpenRC 等服务管理差异。

禁止通过 `trusted=yes`、`gpgcheck=0`、关闭 TLS 校验等方式绕过供应链验证。

### 5. 源码编译安装

源码编译章节至少包含：

- 为什么需要编译，以及官方软件包为何不能满足需求。
- 固定的源码版本和获取最新版的官方入口。
- 对于由 daemon、CLI、运行时、插件等多个上游组件组成的软件，列出组件边界、版本锁定来源和兼容关系；优先使用产品发布构建固定的组件组合，不得把各仓库的“最新版”未经联调直接拼装。
- 源码包的 GPG 签名或 checksum 验证；只下载不验证不算完整流程。
- 各发行版编译工具和开发依赖。
- `configure`、CMake、Meson 或对应构建参数，并解释关键参数用途。
- 独立系统用户、配置目录、日志目录、缓存或数据目录及权限。
- 编译、安装、服务单元、开机启动和日志轮转。
- 实际编译参数的留存方式，例如 `software -V`、构建日志或构建清单。
- 新版本升级、旧二进制备份、回滚和卸载边界。
- 动态模块、ABI、系统库和安全更新责任。

源码编译默认不具备包管理器的文件清单、依赖升级和自动卸载能力。文档必须直接说明这项维护成本，不能只展示 `make && make install`。

### 6. 验证

安装完成后至少验证：

- 客户端和服务端版本。
- 版本来源、编译参数或已加载模块。
- 配置语法或内置自检命令。
- 服务是否运行、是否开机启动。
- 本机最小功能闭环，例如 HTTP 请求、端口连接、测试容器或简单查询。
- 错误日志和服务日志中没有明显异常。

只执行 `--version` 不能证明服务安装成功。

### 7. 安全与系统集成

- 说明防火墙、云安全组、SELinux、AppArmor 和权限影响。
- 服务使用独立低权限用户；需要高权限组或 socket 时明确其等价权限。
- 默认不把数据库、缓存、管理后台等敏感端口暴露到公网。
- 说明日志轮转、数据持久化、证书和备份责任。
- 便捷脚本应先下载、检查和 dry-run；生产环境不得直接使用 `curl ... | sh`。

### 8. 日常运维

- 给出安全重载、重启、状态检查和日志查看命令。
- 给出升级流程，并区分“重新加载配置”和“加载新二进制”。
- 给出回滚入口和卸载说明；默认保留数据和配置。
- 收录高频且可判断的故障，不堆积临时调试日志。

## 文档结构建议

安装类知识笔记默认采用：

```md
# Linux 安装软件名

一句话结论和推荐方式。

## 版本与安装方式选择
## 支持范围
## 安装前检查与备份
## 官方软件包安装
## 源码编译安装
## 配置目录与系统集成
## 验证安装
## 升级与回滚
## 防火墙与安全注意事项
## 常见问题
## 相关链接
```

内容较长时，源码编译、离线安装、国内源排障、集群部署等可以拆成同专题下的独立原子文档，由主安装文档统一导航。

## Frontmatter

长期维护的安装文档建议使用：

```yaml
---
tags: [软件名, Linux, 安装, 运维]
status: evergreen
created: YYYY-MM-DD
updated: YYYY-MM-DD
verified: YYYY-MM-DD
source:
  - 官方安装页
  - 官方下载或版本页
---
```

`verified` 表示版本、支持范围、仓库地址和命令最近一次依据官方资料核验的日期，不等于所有命令都在真实主机执行过。实际执行验证应在交付说明中单独写明。
