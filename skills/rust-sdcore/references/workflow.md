# Rust 工具型 Web 项目调试规范

## 本地服务

- 带 Web UI 的 Rust 工具型项目，开发调试时默认分开启动前端 dev server 和后端服务。
- 如果项目提供 `Makefile` 或等价任务入口，必须通过项目任务启动本地服务，例如 `make dev-backend` 启动 Rust API 服务、`make dev-web` 启动 Vite 前端；不要在日常调试中绕过项目任务直接执行底层命令。
- 后端服务使用项目约定的固定端口启动，不要为了临时调试反复更换端口；前端 Vite dev server 也使用固定端口，常规使用 `5173`。
- 前端 dev server 通过 Vite proxy 把 `/api` 转发到后端固定端口；浏览器预览默认访问前端 dev server 地址。
- 前端改动优先通过 dev server 热更新验证，不频繁重新打包静态资源。
- 只改 Vue、CSS、交互、页面布局或前端类型时，不为了“看效果”执行 `cargo build --release` 或重启 release 二进制。
- 后端服务用项目当前配置文件启动，保证数据库、日志目录和线上安装结构一致。
- 只有验证 release 包、内嵌静态资源、安装脚本或线上升级流程时，才重新执行前端 build 并让后端读取打包后的静态资源。

## Agent 模式

- 仅当前项目或明确具备 agent 节点能力的项目适用；没有 agent 概念的项目不需要套用本节。
- 调试 agent 能力时，要同时启动主程序和必要数量的 agent 进程。
- 多节点能力开发时，至少保持两个 agent 同步启动，用于验证批次记录、节点记录、进度 SSE、失败收敛、回滚和重试等多节点行为。
- agent 使用固定的本地节点 key 和 token，避免每次调试重新创建节点导致数据难以对比。
- 主程序重启后，确认 agent 自动重连；涉及重连、心跳、离线状态或任务兜底时，要观察节点状态和最近心跳时间。

## 验证顺序

- 前端交互改动：优先用前端 dev server 验证，再按风险决定是否执行前端 build。
- 后端业务改动：先执行 Rust 编译检查，再跑覆盖对应模型、handler 或 runner 的测试。
- 涉及前后端联动、SSE、agent 或部署流程时，要用本地真实服务链路验证，不只看模拟输出。
