# 提交与发布验收

适用范围：所有 GitHub 写入、原型发布、线上预览及故障排查。发布前必须读取本文件。

## 前置条件

- 必须有明确目标仓库、分支、允许修改的路径以及已连接 GitHub 插件的写入权限；插件不可用时不得宣称提交成功。
- 必须读取目标仓库最新 `AGENTS.md`，以其构建命令、发布目录和版本机制为准。
- 非原型文档只有用户明确要求同步时才提交；原型完成后依 [交互原型](prototypes.md) 自动提交。
- 破坏性覆盖、删除历史或修改已确认决策，必须取得当前任务明确授权。

## PR 优先的提交策略

- 在默认产品仓库执行写入前，读取最新 `AGENTS.md` 和 `standards/git-workflow.md`，以其实际约束为准。不能因 Skill 内的流程描述代替仓库授权。
- **默认走 PR**：交互原型及 Latest/Overview 版本变更、PM/UI 页面与交互、构建和 CI 脚本、项目/模块数据模型、仓库规范变更。
- **可直接提交**：用户明确授权同步的单项目、低风险普通文档小修改；若跨项目、结构性或大规模修改则使用 PR。用户只要求讨论或草稿时不得提交。
- 同一任务尽量汇总为一个短期分支和一个 PR；不要每修改一个文件就创建新的 PR。分支从最新 main 创建，命名采用 `feat/`、`fix/`、`docs/`、`test/` 或 `refactor/`。
- PR 创建后检查真实 CI；失败则修复，不合并。合并前确认最新 head SHA、main 是否变化、是否冲突及用户授权。优先 Squash Merge。用户明确要求只创建 PR 或暂不合并时必须停在 PR 阶段。
- PR 合并后返回 PR URL 和合并后的 SHA（不把分支提交 SHA 冒充最终 SHA）。部署和访问另行核验，不能将 PR 合并视为发布完成。
- 原型完成后的自动提交授权仍有效，默认通过 PR 实施；但无权限、用户明确禁止提交或要求等待时不能绕过。
- 紧急直接写入 main、强制覆盖、历史删除或回滚均须明确授权；回滚优先新建修复 PR 或 Revert，而非重写已归档历史。

## 分阶段验证

1. **提交**：取得真实 Commit SHA；失败时停止并报告。
2. **构建**：运行仓库指定的校验与构建，或读取可信 CI 结果；不能只根据提交成功推断构建成功。
3. **部署**：确认托管平台实际部署的 Commit 与目标版本一致。部署失败时不得声称已上线，必须报告失败阶段；无法访问平台时标注部署未验证。
4. **访问**：请求真实页面、关键静态资源及版本标识，核对 HTTP 响应与页面内容；仅已知域名不构成成功证据。
5. **故障**：定位构建日志、部署产物和线上响应的具体差异；禁止无依据重复改 CSS 或宣称缓存是根因。

## 结果格式

必须包含项目、文档类型或原型版本、修改路径、真实 Commit SHA、在线地址（如适用）、构建状态、部署状态、访问验证状态。缺失的证据写“未验证”，不得补造 SHA、URL 或成功结果。

## 完成标准

所有声称成功的环节必须有实际工具结果或平台证据；发布失败必须说明阻断步骤及后续核验对象。

## 多会话并行交付与自动合并

- 多个 ChatGPT 会话和本地 Codex 同时修改 product-docs 时，默认每任务使用独立分支与 PR；即使是普通文档，也不得因旧规则允许低风险直推而跳过并发检查。
- 写入前重新读取目标仓库最新 standards/git-workflow.md；提交前比较远端 main 和目标文件版本。PROJECTS.md、AGENTS.md、site/index.html、Latest、Overview、CI 工作流属于共享资源。
- 只有用户已授权自动合并、PR 非 Draft、所有适用的必需 CI 检查真实成功、无冲突、无待人工验收事项时才可自动 Squash Merge；不能把未配置 CI 或检查缺失当作通过。
- 自动合并前重新检查 PR head SHA 和 main 状态；冲突、失败或版本漂移时停止，保留 PR，禁止强推或覆盖。GitHub 套餐限制导致保护规则不生效时必须明确告知。
- 合并代码与部署生产站点严格分离；main 的更新不构成部署授权。任何自动发布关闭的声明都必须有 GitHub Actions 与托管平台配置核验证据。
